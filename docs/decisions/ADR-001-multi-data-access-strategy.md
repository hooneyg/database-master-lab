# ADR 001: 멀티 데이터 액세스 전략 채택 (Spring Data JPA vs MyBatis vs JdbcTemplate)

## 1. 배경 (Context)
엔터프라이즈 환경에서 단일 ORM이나 SQL Mapper만으로 모든 요구사항을 완벽하게 만족시키기는 어렵습니다. 
JPA는 객체 지향적인 도메인 모델링과 개발 생산성에 강점이 있지만, 복잡한 통계 쿼리나 대량의 데이터 처리(Bulk Insert 등)에서는 오히려 성능 병목이 발생할 수 있습니다. 반면, MyBatis나 JdbcTemplate은 저수준 제어와 성능에 유리하지만 유지보수 비용이 증가합니다.

## 2. 대안 (Alternatives)
- **대안 1: 단일 JPA + QueryDSL 전략**
  - 장점: 도메인 중심의 일관된 코딩 가능.
  - 단점: 복잡한 조인, 윈도우 함수 사용, Bulk 연산에 한계가 있음.
- **대안 2: 단일 MyBatis 전략**
  - 장점: DBA 친화적, SQL 세밀 제어 가능.
  - 단점: 단순 CRUD 반복, 유지보수 시 객체-관계 불일치 극복 비용 증가.
- **대안 3: 혼합 전략 (CQRS 패턴의 약식 형태)**
  - 명령(Command)과 쿼리(Query)의 특성에 따라 도구를 분리하여 사용.

## 3. 결정 (Decision)
**대안 3 (혼합 전략)**을 채택합니다.
- **JPA & QueryDSL:** 일반적인 CRUD, 엔티티의 상태 변경, 단순~중간 복잡도의 동적 쿼리에 사용합니다. 도메인 중심 설계를 강제하기 위함입니다.
- **MyBatis:** 특정 벤더에 종속적인 SQL 문법이나, 다수의 테이블 조인이 수반되는 복잡한 통계 쿼리(Read-Only)에 제한적으로 사용합니다.
- **JdbcTemplate:** 대규모 데이터(수만~수십만 건)의 Bulk Insert/Update 처리가 필요한 배치 작업 시 압도적인 성능 확보를 위해 사용합니다.

## 4. 결과 (Consequences)
- **긍정적 효과:**
  - 개발 생산성 향상(JPA)과 극단적 성능 튜닝(JDBC/MyBatis) 두 마리 토끼를 잡을 수 있습니다.
  - 상황에 맞는 도구를 선택할 수 있는 유연성을 아키텍처 레벨에서 보장합니다.
- **부정적 효과:**
  - 여러 기술 스택이 혼재하므로 팀원의 학습 곡선(Learning Curve)이 상승합니다.
  - 트랜잭션 매니저를 여러 개 사용해야 할 수 있으며(본 프로젝트에서는 동일 DataSource를 사용하여 해결), 일관성 관리에 주의가 필요합니다.
